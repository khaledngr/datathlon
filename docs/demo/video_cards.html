DATATHLON.
Datathlon · data pipeline in production

From the shop floor
to the decision

One real run of our pipeline, recorded without cuts: data arrives with errors, the pipeline catches them, and the managers see clean numbers.

Sources→Cloud Storage→Bronze→Silver + Quarantine→Gold→Dashboard
Step 1 · 05:30 every morning

The company side
wakes up

Cloud Scheduler starts our Docker job on Cloud Run: it reads yesterday's web orders from the shop's Postgres database (incremental) and drops the till, stock and API files in the landing bucket.

Google Cloud console · datathlon-morning-job
Step 2 · landing zone

Raw files,
as the systems send them

One folder per source and per day in Cloud Storage (Frankfurt, same region as Snowflake). Nothing is cleaned here.

Bucket datathlon-landing-513514 · tills · stock · api
Step 3 · during the day

The store tills send sales,
with errors

A new file every 5 seconds. On purpose, like real tills: duplicates, missing IDs, unknown products, quantities like "two", prices in cents, dates in 2099, store names spelt five ways.

Terminal · till_feed.py --live
Step 4 · 06:00 every morning (started now)

Snowflake runs
the pipeline

A graph of Snowflake Tasks: load the till, stock and API files (COPY INTO), check the web load, then dbt builds and tests every table. If anything fails, dbt does not run and the team gets an e-mail.

Snowsight · task graph OPS.T_START
Step 5 · Bronze

Every line kept
exactly as received

Nothing is rejected at load: each line is stored raw, with the file and line number it came from. The loyalty card number is masked for engineers.

Snowsight · BRONZE.TILL_SALES_RAW
Step 6 · Quarantine

A bad line never
reaches the numbers

dbt checks every line against 9 rules. A line that breaks one goes to quarantine with its reason, next to the line as it was sent: the store can be told exactly what to fix.

Snowsight · QUARANTINE.QUARANTINE_TILL_SALES
Step 7 · Silver

What can be fixed
is repaired

Store names mapped to one code, prices in cents divided by 100 against the catalogue, quantities written as text, three date formats. Then nothing is lost: every raw line is in silver or quarantine, exactly once, checked by a test.

Snowsight · SILVER.SILVER_TILL_SALES
Step 8 · a whole file is broken

Half a stock count
is refused whole

The stock export stops mid-file. The load aborts, the automatic retry aborts too, not one line is loaded: the dashboard keeps yesterday's stock instead of a wrong one.

Terminal · 02_broken_stock_file.py
Step 9 · tests and lineage

Every table built
and tested by dbt

67 tests on every run, inside Snowflake: keys, accepted values, relationships, gold revenue equal to silver, a day counted by hand. The lineage shows where every number comes from.

dbt docs · GOLD.DBT_RUN_RESULTS
Step 10 · Gold

One table
per decision

Sales per day for the category managers (UC1), days of stock cover for the supply chain (UC2), and the data quality of every store. Complete days only.

Snowsight · GOLD
Step 11 · the decision

The dashboard,
inside Snowflake

A Streamlit app that runs in Snowflake, with a read-only role that sees Gold only, on its own warehouse that sleeps after 5 minutes.

Snowsight · Streamlit · Datathlon · sales and stock
Step 12 · run and govern

Logged, masked,
paid for

Every run is logged and e-mails on failure. Personal identifiers are masked by tag. Every credit belongs to a team (showback), with budgets and caps.

Snowsight · OPS.PIPELINE_RUNS · GOLD_COST_SHOWBACK_DAILY
Datathlon · Group 8

Bad data in,
clean decisions out

Google Cloud · Snowflake · dbt · Terraform · Streamlit. Every step automated, every number traceable to its line.
